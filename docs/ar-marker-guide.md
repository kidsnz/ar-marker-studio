# ARマーカー技術ガイド

ATARI AR で使う NFT マーカーの仕組み、品質の測り方、チューニング手順をまとめる。
2026-08-10 に ARToolKit5 のソースを読み、ローカルに生成環境を再現して実測した結果に基づく。
**推測は含めず、実測とソースの根拠があるものだけを書く。未検証のものは明示する。**

---

## 1. 仕組みの全体像

NFT（Natural Feature Tracking）は2つの独立した仕組みで動く。ここを分けて考えないと原因を見誤る。

| 段階 | 役割 | 使うファイル | 中身 |
|---|---|---|---|
| **検出** | カメラ映像の中からマーカーを見つけ、最初の姿勢を決める | `.fset3` | FREAK記述子のキーフレームセット |
| **追従** | 見つけた後、毎フレーム姿勢を更新し続ける | `.fset` | テンプレートマッチング用の特徴点 |
| （共通） | 距離ごとの縮小画像 | `.iset` | JPEG圧縮の画像ピラミッド |

**症状の切り分けはここから始める。**

| 症状 | 疑うところ |
|---|---|
| そもそも認識しない | `.fset3`（検出）が弱い |
| 認識はするが姿勢が暴れる | **`.fset`（追従）の点が足りない** |
| 認識も追従もするが奥行きだけ揺れる | カメラパラメータ、距離帯の切り替え、フィルタ設定 |

## 2. `.fset` の読み方

追従点の数は**実機テストの前に**数えられる。これが品質判定の中核になる。

### バイナリ構造（ARToolKit5 `AR2FeatureSetT`、リトルエンディアン）

```
int   レベル数
  各レベルごとに:
    int   scale
    float maxdpi      ← maxdpi が先。逆に読むと距離帯の判定が反転する
    float mindpi
    int   点数
    AR2FeatureCoordT × 点数   （= float x, y, mx, my, maxSim の20バイト）
```

パーサは `tools/parse_fset.py` に置いてある。

```bash
python3 tools/parse_fset.py ../website/projects/atariar/markers/<name>/01.fset
```

### 判定の目安

**合計点数は当てにならない。実際に使う距離帯の点数だけを見る。**
合計92点でも、その帯に14点しかないことがある（satoshi-tomiie-bassline/03 が実際にそう）。

縦持ちで使える点数と、実機での体感（2026-08-11 に実測）:

| 縦持ちで使える点 | 実機での体感 | 実例 |
|---|---|---|
| 14点 | 安定 | satoshi-tomiie-bassline/03 |
| 9点 | ほぼ安定（わずかに症状） | satoshi-tomiie-bassline/02 |
| 3点 | **大小に飛んで使えない** | satoshi-tomiie-bassline/01 |

判定は `tools/parse_fset.py` が自動で行う。**ツールを変更したら必ず `--self-test` を通すこと。**

**※ この表の読み方は下で決着している（測る範囲が重要）。**

**中央で測る限り**この目安と整合する。

#### 効いている量はこれだけ

    画面に写る幅(px) = 304.8 × 実寸mm ÷ 距離mm

    181px 超  … 画面からはみ出す（中央だけが使われる）
     82px 以上 … 3点に届く（公開中の全マーカーでの実測の下限）
     44px 未満 … テンプレートが収まらず構造的に0点

**生成時に宣言する実寸（`-dpi`）は結果を変えない。** 帯の画像の幅も画面上の幅も
`dpi × 宣言インチ` なので約分で消える。だから同じマーカーが 4cm のステッカーでも
1270mm の絵でも同じように動く。実寸を意識せず運用できていたのはこのため。

#### 実際の使われ方（判定はこの3つに合わせてある）

| 場面 | 実寸 | 距離 | 画面に写る幅 |
|---|---|---|---|
| ペインティング | 50〜70インチ（works ページ記載） | 1.5〜2m | 194〜361px（**必ずはみ出す**） |
| ラップトップ画面 | 80〜146mm（14インチで実測） | 30〜50cm | 49〜149px |
| ステッカー | 4〜5cm | 20〜30cm | 41〜76px（**崖の下**） |

ステッカーは計算上は3点に届かないが、実機では問題なく動いている。
実行時のフォールバック（帯に点が無いと `[mindpi/2, maxdpi*2]` まで探しに行く）に
助けられていると思われる。3点に確実に届かせたいなら 4cm なら15cm、5cm なら19cmまで寄る。

### なぜその点数なのか（実行時のソースで裏が取れた）

上の目安は当初は実機の体感だけが根拠だったが、`lib/SRC/AR2/tracking.c` と
`selectTemplate.c` を読んで機械的な理由が分かった。**「点が何点あればいいのか」を
決めているのは生成側ではなく実行時のこの2つ。**

| 事実 | ソース | 意味 |
|---|---|---|
| **3点を切ると追従が止まる** | `tracking.c`: `if(num < 3) return -3` | satoshi/01 はちょうど3点。1点失えば終わる |
| **1フレームで試すのは16点まで** | 後述（既定の10ではない） | 90点あっても毎フレーム16点。**数より散らばり** |
| **画面の外周1/8の点は選ばれない** | `ar2SelectTemplate` の座標チェック | 帯の画像が176pxより大きいときだけ効く（それ未満はテンプレートの22px制約が先） |
| **帯に点が無ければ `[mindpi/2, maxdpi*2]` で再検索** | `extractVisibleFeatures` | 厳密な帯判定は少し厳しめに出ている |
| **帯の選択は縦横の見かけdpiの小さい方** | `ar2GetResolution2` が `dpi[1]` に小さい方を入れ、`w[1]` で判定 | `min(幅基準, 高さ基準)` という既存の式が正しいと確認できた |

### 【訂正】実行時の値は ARToolKit5 の既定と違う

上の表は当初 ARToolKit5 の `config.h` の既定値で書いていたが、**私たちが実際に使っている
jsartoolkitNFT は起動時にそれを上書きする**。`ARToolKitNFT_js.cpp` の `setupAR2()`:

```cpp
ar2SetTrackingThresh(ar2Handle, 5.0);      // 姿勢誤差の上限
ar2SetSimThresh(ar2Handle, 0.50);          // 追従点として採用する類似度
ar2SetSearchFeatureNum(ar2Handle, 16);     // ← 既定の 10 ではなく 16
ar2SetSearchSize(ar2Handle, 6);
ar2SetTemplateSize1(ar2Handle, 6);         // ← 生成時の 11 とは別物
ar2SetTemplateSize2(ar2Handle, 6);
```

「3点未満で追従停止」は変わらない。**変わるのは「1フレームで試す点数」で、10 ではなく 16。**
`tools/parse_fset.py` の `TRACK_PER_FRAME` も、ar-marker-studio の `js/engine.js` も 16 に直してある。

### 検出側のしきい値（2026-08-12 にソースで確定）

追従側と違い、検出側の条件は全部コンパイル時固定でオプションから変えられない。

| 条件 | 値 | どこ |
|---|---|---|
| 記述子マッチの ratio test | 1位/2位 < **0.7** | `feature_matcher-inline.h` |
| マッチ数の下限 | **8点** (`kMinNumInliers`) | `visual_database-inline.h` |
| 再投影誤差の許容 | **3px** (`kHomographyInlierThreshold`) | 同上 |
| ホモグラフィの妥当性 | 四隅が凸、かつ最小三角形が参照面積の **0.01%** 以上 | `visual_database.h` |
| 姿勢の ICP 残差 | **10.0 以下** | `kpmMatching.cpp` |
| 入力から取る特徴点の上限 | **500点** | `visual_database-inline.h` |

**検出は完全に1フレームで完結する。** フレーム間に蓄積する仕組みはどこにも無い。

**スケールは不変。** Hough 投票が許すのは log10(入力/参照) が ±0.9、つまり
**0.126倍〜7.94倍**。`.fset3` の段が入力の大きさと合っている必要は無い。

**一度検出すると `detectedPage` が立ち、以後 KPM は走らない。** 追従が切れて -2 に戻るまで
再検出しない。同じ画像で検出テストを繰り返すと、2回目以降は追従を見ていることになる。

### 散らばり（追従の姿勢を決めるもの）

`ar2SelectTemplate` は追従の最初の4点をこう選ぶ。

| 何点目 | 選び方 |
|---|---|
| 1点目 | 画面中心から**最も遠い**点 |
| 2点目 | 1点目から**最も遠い**点 |
| 3点目 | 1〜2点目を結ぶ線から**最も離れた**点 |
| 4点目 | **四角形の面積が最大**になる点 |
| 5点目以降 | 前フレームで追えた点、無ければランダム |

**分布は経験則ではなくアルゴリズムそのもの。** 同じ点数でも固まっていれば
小さい四角形しか作れず、姿勢が不安定になる。

ツールはこれを「散らばり」（点の凸包の面積がマーカー全体の何割か）として出す。

> **【2026-08-15 撤回】下の表を合否の基準に使ってはいけない。**
> 散らばりは**参考値**で、**合否は「3点の下限」だけ**で判定する。
> この表は satoshi の3枚で点数と散らばりが一緒に動いていたもので、
> 例を7本に増やすと安定なものが 1.8%〜22.4% に散らばり、何も予測しなかった。
> 詳細は第2章の撤回ブロックと `ar-marker-studio/CHANGELOG.md` の v2.3.0。
> 以下は撤回前の表。経緯として残す。

| 散らばり | 点数 | 実機での体感 |
|---|---|---|
| 1% | 3点 | 大小に飛ぶ |
| 17% | 9点 | ほぼ安定 |
| 33% | 14点 | 安定 |

**【重要】マーカーが画面より大きく写るときは、見えている中央だけで測る。**
大きい絵は必ずはみ出すので、隠れている部分の点まで数えると実機と食い違う。
中央で測って初めて emoticons/01（実機で揺れる）が 0.6%、
pizzaboy/07（問題なし）が 19.5% と分かれた。第2章の決着を参照。

`--self-test` はこの順序が崩れていないかも検算する。

### 検出側（.fset3）も距離帯ごとに数えられる

`.fset3` の形式も解読済み（実ファイル25個で末尾ぴったりを確認）。

```
int 点数
  各点: coord2D(8) + coord3D(8) + FreakFeature(108) + pageNo(4) + refImageNo(4) = 132バイト
        FreakFeature = 記述子96バイト(768ビット) + angle(4) + scale(4) + maxima(4)
int ページ数 → 各段の {幅, 高さ, 段番号}
```

各点が `refImageNo` でどの段のものかを持っているので、**距離帯ごとの検出キーポイント数**が出せる。
**0点の帯は、追従点がいくらあってもその距離では認識できない。**
「認識しない」と「認識するが揺れる」の切り分けがこれで付く。

`parse_fset.py` は常に、Web版は生成後に表示する。

### 繰り返し模様の判定は作らなかった

記述子（FREAK、768ビット）を使えば「離れた場所に瓜二つの点がある＝繰り返し模様」を
数値化できるはずだった。マッチャは ratio test（1位/2位 < 0.7）なので、
瓜二つの点が複数あると1位と2位の差がつかず棄却される、という筋も通っている。

**やめた理由は閾値を決める材料が取れなかったこと。** 手元のマーカーは全部ちゃんと
認識するので、負例が1つも無い。指標を作っても正しいか確かめようがない。

ただし**検出できるかどうか自体は、合成画像を検出器に流せば測れる**（2026-08-12 に成立）。
やり方と実測値は第11章。繰り返し模様の判定を作るなら、まずそこで負例を作ってから。

**この件で学んだこと: 較正を最後に回してはいけない。**
一度は「合成映像では検出できない、方式が成立しない」と結論した。
実際には測定器の側が例外で固まっていただけで、画像は最初から正しかった。
「この測定器はそもそも何かを検出できるのか」を最初に確かめていれば、20秒で分かった。

### 使える距離

`website/projects/atariar/data/camera_para.dat` は 640x480 基準で `fx=609.37, fy=606.52`。
長辺方向の画角は `2*atan(320/609.37) = 55.4度`。ここから距離ごとの見かけdpiが出る。

```
処理キャンバス上の焦点距離 = (長辺px / 2) / tan(画角/2)
   長辺px = 横持ち 320 / 縦持ち 240（縦持ちは映像が回るので長辺が240になる）
見かけdpi = 焦点距離 / 距離mm × 25.4
マーカーが画面に収まる最短距離 = 焦点距離 × max(幅mm/横px, 高さmm/縦px)
```

この式は既存の「画面いっぱいに写るときの見かけdpi」と一致する（307mm角なら
どちらの持ち方でも 39cm で画面いっぱいになり、そこでの dpi が既存の式と小数点以下まで一致）。

**注意: 点数は距離に対して滑らかに減らない。** 距離帯どうしの重なり方が不規則なので、
点数は上下に飛ぶ。satoshi/03 の縦持ちの実測:

| 距離 | 39cm | 41cm | 43〜47cm | 49cm | 51〜59cm | 61cm | 63〜73cm |
|---|---|---|---|---|---|---|---|
| 点数 | 14 | 8 | 8 | 12 | 4 | 7 | 3 |

「最小〜最大」で答えると嘘になるので、ツールは**最も長く連続する区間**と、
区間がいくつに分かれているかを出す。

## 3. 追従点が採用される条件

`lib/SRC/AR2/featureMap.c` の実装。生成時に呼ばれるのは `ar2SelectFeature2`（`ar2SelectFeature` ではない）。

### 手順

1. **候補を絞る**（`ar2GenFeatureMap` 前半）
   3×3 の勾配を取り、**4近傍すべてより大きい画素**だけを残す。
   さらに 1000段のヒストグラムを強い順に積み、**画素数の2%**に達したところで足切りする。
   **ここを通らなかった画素は、以降どうやっても特徴点にならない。**
   ログの `Extracted features`（極大点の数）と `Filtered features`（足切り後）がこれ。

2. **featureMap を作る**（同・後半）
   残った候補について、**45×45**のテンプレート（`AR2_DEFAULT_TS1=11 × AR2_TEMP_SCALE=2`）を作り、
   **半径2より外・±10以内**（21×21の正方形から半径2の円板をくり抜いたドーナツ）での
   最大類似度を記録する。0.95 を超えた時点で打ち切る。
   この段階の閾値は `MAX_SIM_THRESH2=0.95` と `SD_THRESH2=5.0` で**固定**され、
   コマンドラインオプションの影響を受けない。

3. **featureMap の値が小さい順に点を採る**（`ar2SelectFeature2`）
   採用の条件は次の3つすべて。
   - featureMap の値が `max_sim_thresh` 未満（＝近傍と紛らわしくない）
   - テンプレートの輝度標準偏差が `sd_thresh` 以上（＝コントラストがある）
   - **近傍±2px での相関の最大が 0.99 以下**（＝1〜2pxずらすと確実に違って見える）

4. 採用した点の周囲 `occ_size` を塗り潰して、点が密集しないようにする
   （**内部で `occ_size *= 2` される**ので、実効的な最小間隔は設定値の2倍）

上限は `(幅/occ)×(高さ/occ) + (幅/135)×(高さ/135)` 点（ログの `Max feature`）。

### 決定的に重要な点

手順1を見落とすと、予測が5倍に膨らむ。**相関は全画素で測られてはいない。**

条件3の **0.99 はソースにハードコードされていて、オプションで変えられない**。
「1〜2px ずらしても同じに見える場所」は、何をしても絶対に特徴点にならない。

そして判定基準は一貫して「**近傍±10px と紛らわしくないか**」であり、
人間が見て特徴的かどうかとは無関係。

## 4. `-level` が変えるもの

`include/AR2/config.h` の定数。既定は `level=2`。

| level | max_thresh | min_thresh | sd_thresh | occ_size（実効値） |
|---|---|---|---|---|
| 0 | 0.80 | 0.70 | 12.0 | 24（48） |
| 1 | 0.85 | 0.65 | 10.0 | 24（48） |
| **2（既定）** | 0.90 | 0.55 | 8.0 | 16（32） |
| 3 | 0.98 | 0.45 | 6.0 | 16（32） |
| **4** | 0.98 | 0.45 | 6.0 | **12（24）** |

level=4 が効くのは、`max_thresh` が 0.90 → 0.98 に緩むことと、
点の最小間隔が 32px → 24px に詰まることの両方による。

`-leveli`（0〜3、既定1）は検出側（`.fset3`）の密度を変える。追従の安定性には効かない。

## 5. 何が効いて何が効かないか（全部実測）

対象は satoshi-tomiie-bassline（Atari 2600 の画面出力、320×228）。

| 手 | 追従点 | 判定 |
|---|---|---|
| そのまま（level=2） | 8 | 基準 |
| `-level=4` だけ | 15 | 効くが不足 |
| 別フレームの絵に差し替え | 8 | **効かない** |
| タイトル文字を合成 | 15 | ほぼ効かない |
| `-dpi` を変える（27 / 13） | 14 / 14 | **効かない**（距離帯が動くだけ） |
| 2倍に拡大（level=2） | 17 | 効く |
| 4倍に拡大（level=2） | 25 | 効く |
| **2倍拡大 + level=4** | **38** | 実用ライン |
| **4倍拡大 + level=4** | **71〜80** | 十分 |

### 結論

**絵の内容を変えるより、解像度を上げて level を上げる方が圧倒的に効く。**

拡大が効く理由は、ブロックの繰り返し周期が判定基準の「半径10px」より長くなるため。
拡大は必ず**ニアレストネイバー**で行う（補間するとエッジが鈍って逆効果）。
拡大しても絵そのものは変わらないので、作品としての見た目は保たれる。

### 当てにならなかった指標

生成前に画像から品質を予測しようとして、次を試したが**外れた**。

- Shi-Tomasi のコーナー性（最小固有値）… コーナー性22%の画像でも8点だった
- 勾配方向の偏り（横エッジ率）… 相関しなかった
- 24×24パッチの自己相似度（近傍16px除外）… 相関しなかった

ARToolKit の判定は「45×45テンプレート、近傍**±10px のドーナツ**、しきい値0.95固定」という
特定の条件なので、これと同じ条件で測らないと予測にならない。
**同じ条件で測れば予測できる**ことは第10章で確認済み（`tools/predict_features.py`）。

## 6. DPI と距離帯の設計

ここを外すと、点が足りていても実使用で使えない。

### DPI は「マーカーの実寸」を宣言するもの

```
実寸（インチ） = 画像の幅（px） ÷ dpi
dpi = 画像の幅（px） ÷ 実寸（インチ）
```

例: 640px の画像を 12インチ（305mm）のレコードジャケットに印刷する → `dpi = 640 ÷ 12 ≒ 53`

### 距離帯（scale）ごとに特徴点が分かれている

`.fset` の各レベルは `mindpi`〜`maxdpi` の有効範囲を持つ。
実行時、ARToolKit はカメラから見た**見かけの解像度**を計算し、対応するレベルの点を使う。

**ARnft が画像処理する解像度は 320×240 で固定。** `ARnft.js` の `prepareImage()` に
320 がハードコードされていて、カメラが何を返してもここまで縮められる。
さらに**縦持ちすると映像が左右に黒帯で letterbox され、実効 180×240 になる**。

```
見かけdpi = min( 実効幅px ÷ マーカー幅（インチ）, 240 ÷ マーカー高さ（インチ） )
   実効幅px = 横持ち 320 / 縦持ち 180
```

マーカーの縦横比で「幅で決まるか高さで決まるか」が変わる。正方形は高さで決まるため、
4:3 のマーカーより見かけdpiが下がる。12インチ（305mm）のジャケットの場合:

| 持ち方 | 見かけdpi |
|---|---|
| 横持ち | 26.7 dpi |
| **縦持ち** | **15.0 dpi** |

**この前提を「カメラは640px」と取り違えると判定が3.5倍ずれる。**
実際にこの取り違えをやらかし、正常に動いているマーカーを「0点」と誤判定していた
（2026-08-11 に `--self-test` で検出して修正）。

### 実例：satoshi-tomiie-bassline の推移（すべて縦持ち・実機で体感を確認済み）

| マーカー | 絵 | 合計 | 縦持ちで使える点 | 実機での体感 |
|---|---|---|---|---|
| 01 | cover-fsharp | 38 | **3点** | 大小に飛ぶ |
| 02 | cover-fsharp_1 | 46 | **9点** | ほぼ安定 |
| 03 | cover-fsharp_8（正方形＋枠＋白ブロック） | 92 | **14点** | 安定 |

**合計92点でも、実際に使う帯には14点しかない。** 合計を見ても意味がない。

### `-dpi` は点数を変えない

`dpi` を変えると距離帯の値は動くが、**どのレベルが選ばれるかは変わらない**。
`見かけdpi ÷ 宣言dpi = 実効幅px ÷ 画像幅px` で、両辺が同じ比率で動くため。
実測でも dpi=72/27/13 で 15/14/14 点とほぼ変化しなかった。

**選ばれるレベルを動かせるのは元画像の幅だけ**（実効幅px ÷ 画像幅px の比）。
ただし実測では 224/320/448/640px を試して 640px が最良で、小さくしても改善しなかった。

## 7. 生成手順

### Web版（通常はこれで足りる）

https://kidsnz.github.io/NFT-Marker-Creator/ （self-host、`kidsnz/NFT-Marker-Creator` fork）

UIにオプションがある。チェックボックスで有効化して数値を入れる。

| オプション | 既定 | 範囲 | 用途 |
|---|---|---|---|
| `level` | 2 | 0〜4 | 追従点の密度。**基本は4にする** |
| `leveli` | 1 | 0〜3 | 検出側の密度 |
| `dpi` | 72 | 任意 | マーカーの実寸を決める |
| `sd_thresh` | 8 | 6〜12 | コントラストの下限 |
| `max_thresh` / `min_thresh` | level依存 | | 個別調整用 |

PNG入力の場合、画像側のDPI情報は無視されて 72 固定になる。JPEGは EXIF の解像度を読む。

### 【最重要】アルファ付きPNGを入れてはいけない

`app.js` の `rgbaToRgb()` は壊れている。アルファ値を 0〜1 として扱うべきところを
0〜255 のまま計算するうえ、返ってきた3バイト/画素の配列を4バイト刻みで読み直すため、
**画像が横に4〜5回繰り返され、階調も反転した別物になる**。

2026-08-11 に実測して確認した。`floralroids/01.png`（RGBA）を通すと、
`.iset` に入る画像はこうなる（左が入力、右が生成器の中で実際に使われた画像）:

- 入力: 630×564 のインベーダー柄
- 実際: 同じ絵が横に5回繰り返され、白黒が反転し、走査線状の縞が乗ったもの

**生成前に必ず背景を塗り潰して RGB にすること。** JPEG なら構造上アルファを持てないので安全。
`tools/predict_features.py` はアルファを検出したら警告を出す。

該当するのは `floralroids/01` `floralroids/02` の2枚（どちらも現行のマーカーは
この壊れた画像から作られている）。

### ローカルCLI（反復実験に向く。これが速い）

`kidsnz/NFT-Marker-Creator` を clone して `npm install` するだけ。
新しい Node では **1ファイル足すだけ**で動く（vendor 側を書き換える必要はない）。

`run.js`:

```js

// ブラウザ経路に入ってファイルパスを fetch しようとして落ちる。隠せば fs 経路に戻る

```

```bash

```

- **`-NoConf` は付けない。** 名前に反して、付けると「続けますか？(Y/N)」の

- 生成時間は **210×210 で1秒、720×720 で3秒、500×751 で9秒**。
  「2〜4分かかる」のは Web 版の話で、ローカルCLIはこの程度で終わる。

ログには `ar2SelectFeature2` が選んだ点が1点ずつ出る。**これが唯一の答え合わせの手段。**

```bash
node run.js -i ./in/src.png -o out -level=4 -dpi=53 2>&1 | grep -E "^\[info\] +[0-9]+: \("
```


## 8. 品質チェックの手順（実機に渡す前に）

**生成する前に予測する**（第10章）→ 良さそうなら生成する、の順で回すのが速い。

1. `python3 tools/predict_features.py <画像> --dpi <画像幅px ÷ 実寸インチ> --level 4`
2. **「縦持ちで使える点」が 3点を割っていない**か確認する（合計点数は見ない）。
   **合否はこの下限1本**（3点未満で追従が止まる、というソース由来の仕様）。
   ※ 以前ここに書いていた「12点以上」は 2026-08-15 に撤回した。余裕の目安が
   欲しいときは第2章の実測表（9点=ほぼ安定 / 14点=安定）を参考にする
3. 足りなければ `--heatmap out.png` で弱い場所を見て、第9章の「効く手」を試す
4. 通ったら生成する（`-level=4`、同じ `-dpi`）
5. `python3 tools/parse_fset.py <出力>.fset` で、予測どおりになったか確認する
6. ツール自体を変更したときは **必ず両方の `--self-test` を通す**

### ツールが正しいことをどう確かめるか

**`tools/parse_fset.py --self-test`** … 実機で確認した事実と矛盾しないかを検算する。

- 公開中のマーカー22個が「0点」と判定されないか（実際に動いているのだから0点はありえない）
- satoshi 01 < 02 < 03 の順に点数が上がるか（実機の体感と同じ順序）
- 処理解像度の定数が実測値（320×240 / 180×240）のままか

**`tools/predict_features.py --self-test`** … 生成器のログと一致するかを検算する。

- コントラストのある絵5件で、距離帯ごとの点数と候補数が**完全一致**するか
- のっぺりした絵2件で、許容範囲（10%）に収まるか

どちらの検算も実際に誤りを検出している。**「直したつもり」を信用せず、必ず走らせること。**

| 320×228 | 80.8 KB | 約49 KB |

## 9. 絵をどう作れば点が増えるか（2026-08-11 実測）

satoshi-tomiie-bassline のマーカーを 3点 → 14点 にする過程で、20通り以上を実測した結果。
**すべて縦持ち（実効180px）で「実際に使える点」を測っている。**

### 効いたもの

| 手 | 効果 | 備考 |
|---|---|---|
| **絵を粗くする（大きなブロックを置く）** | 10点 → 14点 | 塊1個で+4点。複数散らせば積み上がる |
| **正方形にする** | 3点 → 9点 | 12インチのジャケットは元々正方形なので自然 |
| **正方形＋外周の枠** | 9点 → 17点 | 枠の太さが要件を満たす場合のみ |
| ニアレストネイバーで2倍に拡大 | 8点 → 15点相当 | 補間拡大は不可（エッジが鈍る） |
| `-level=4` | 8点 → 15点相当 | 既定は2。基本は4にする |

### 効かなかったもの（もう試さなくてよい）

| 手 | 結果 |
|---|---|
| 枠の太さ 3.8mm 以下 | **効果ゼロ**（縮小後3px未満で消える） |
| 枠の位置を内側/外側にずらす | 変化なし |
| 枠を9.5mm より太くする | 変化なし（頭打ち） |
| 二重線・三重線・破線・目盛り | いずれも本体の枠に劣る |
| 上下だけの帯（左右なし） | 11点止まり。四辺揃えると21点 |
| **白黒2値化** | **大幅に悪化**（9点 → 2点）。階調が識別の手がかりになっている |
| ディザ（細かい点描） | 2点。180pxまで縮むと平均化されて消える |
| 横長にする（16:9） | 1点。縦持ちでは幅で決まるので不利 |
| `-dpi` の変更 | 変化なし |
| 元画像の幅を変える（224/320/448px） | 640px が最良のまま |
| 4倍に拡大 | 2倍より悪い（使う帯から外れる） |

### 設計則（実測から確定）

1. **グレーの階調を残す**（2値化は禁物。この絵は7〜8段階持っている）
2. **線・枠は縮小後3px以上残る太さに**（12インチで最低5.7mm、9.5mmで頭打ち）
3. **四辺すべてに構造を置く**（上下だけでは横方向の位置が決まらない）
4. **正方形か4:3にする**（横長は縦持ちで不利）
5. **細かい模様は無駄**（ディザ・細線・2px枠はすべて効果ゼロ）
6. **大きな塊を離して複数置く**（1個で+4点、位置は離すほど良い）

**方向は「粗く・太く・階調を残す」。** 細かくする方向は全部外れた。

## 10. 生成せずに品質を測る（2026-08-11 完成）

`tools/predict_features.py` が、**元画像だけから追従点を予測する**。
生成器を回さずに、`parse_fset.py` と同じ判定表がそのまま出る。

```bash
python3 tools/predict_features.py <画像> --dpi 53 --level 4
python3 tools/predict_features.py <画像> --dpi 53 --heatmap out.png
python3 tools/predict_features.py --self-test
```

### 精度

**12通り（画像9枚 × level 0〜4 × dpi 40〜150）を、生成器のログと全点・全距離帯で
突き合わせて検証した。**

| 一致の度合い | 件数 | 中身 |
|---|---|---|
| **1点残らず一致**（座標・点数・候補数） | 7 | satoshi 01/03、x/01、x/02、emoticons/01、pizzaboy/06、marslander/02 |
| 点数・候補数は一致、座標が数点入れ替わる | 3 | pizzaboy/07・04、emoticons/02（値差 5e-6 の同着） |
| 数％ずれる | 2 | edo/01（のっぺりしたグラデ） |

実運用の答え合わせも通っている。satoshi の3枚を「元画像を2倍に拡大 → `-dpi=53 -level=4`」で
予測すると、**出荷済みの `.fset` と 41帯中 40帯が一致**した（残り1帯も1点差）。

残差の原因は**すべて生成器側の丸め誤差**。生成器は相関を float32 で 2025 画素ぶん
足し込むので、輝度SDが小さい領域（edo/01 の空は SD≒13）で桁落ちが起き、値が 1e-3 ほど動く。
実際に float32 の逐次加算で追試したところ、生成器のログの値と**小数点以下6桁まで再現**できた
（edo/01 の (203,209) で 0.778344 が一致）。
つまりこちらの float64 の方が数学的には正しく、生成器の方がぶれている。
判定（安定/不足/暴れる）が変わるほどの差ではない。

### アルゴリズムの全体像（ここを外すと必ず過大評価になる）

**全画素の相関を計算しているわけではない。** 3段階で候補が絞られる。

1. **勾配の極大点だけを拾う**（`ar2GenFeatureMap` 前半）
   3×3 の勾配を取り、**4近傍すべてより大きい画素**だけを残す（ログの `Extracted features`）。
2. **さらに画像の2%以内に絞る**
   1000段のヒストグラムを上から積み、**画素数の2%**に達したところで足切りする
   （ログの `Filtered features`）。極大点が2%未満なら全部通る。
3. **残った画素だけ相関を測る**（同・後半）
   45×45 のテンプレートを、**半径2より外・±10以内**（21×21の正方形から半径2の円板を
   くり抜いたドーナツ）のすべての位置と比べ、最大の相関を記録する。
   0.95 を超えた時点で打ち切るので、記録値は真の最大とは限らない。

そのうえで `ar2SelectFeature2` が、値の小さい順に採り、周囲 `occ_size×2` を塗り潰す。

**最初に 44点 対 実際 8点 と外していた原因は、1と2を丸ごと落としていたこと。**
全画素を候補にすれば当然そうなる。ソースの `ar2GenFeatureMap` を後半だけ読むと見落とす。

### 途中で犯した誤り（同じ轍を踏まないために）

| 誤り | 症状 | 正解 |
|---|---|---|
| **勾配NMS＋2%の足切りを落とした** | **予測が5倍に膨らむ** | 候補は全画素ではない（上記1・2） |
| 近傍を半径10の円板とした | 値がわずかに低く出る | **21×21の正方形**から半径2をくり抜く（外側に円の制限は無い） |
| 0.95 の打ち切りを入れなかった | level 3/4 で順序が狂う | 0.95 超えで即打ち切り。記録値は真の最大ではない |
| テンプレートを23×23とした | 予測が過大 | `TS1 × AR2_TEMP_SCALE` = 22 → **45×45** |
| ±2pxの近傍チェックを忘れた | 予測が大幅に過大 | `max > 0.99` で却下。横線の絵はここで大量に落ちる |
| `truncf` の引数の丸めを無視した | **距離帯が全体に 0.02% ずれ、縮小画像が1px変わる** | 下記 |
| JPEGで答え合わせした | 値が数e-4 ずれ、座標も1〜2px動く | **PNGで検証する**。JSのJPEGデコーダと libjpeg は結果が違う |
| JPEG圧縮を疑った | — | 無関係だった |

`truncf` の件は分かりにくいので補足する。最小dpiの計算は

```c
truncf( (28.0f / 短辺) * dpi * 1000.0 ) / 1000.0f
```

で、`* 1000.0` は **double** の定数なので途中まで double で進む。
520×400・dpi=60 だと 4199.9998 になるが、`truncf` の引数は **float** なので
ここで 4200.0 に丸め**上がって**から切り捨てられ、4.2 になる。
float64 のまま切り捨てると 4.199 になり、以降の距離帯が全部 0.02% ずれ、
縮小画像の高さが1px変わり、候補数から下流が全部合わなくなる。
**pizzaboy/07（dpi=60）がちょうどこの境目**なので、`--self-test` に入れてある。

### GitHubのソースの読み方

`ar2GenFeatureMap` の内側除外は、**GitHub master でも生きている**。
コメントアウトされているのは同じ意味の別表現（正方形版）の方:

```c
if( ii*ii + jj*jj <= search_size2*search_size2 ) continue;          // ← これが生きている
//if( jj >= -search_size2 && jj <= search_size2 && ... ) continue;  // ← こちらがコメントアウト
```

以前「master ではコメントアウトされている」と書いたが、それは**この2行を取り違えていた**。
結論（ドーナツ状に見る）は合っていた。

### ヒートマップ（`--heatmap`）

3面を並べたPNGを書き出す。既定では**縦持ちで実際に使う距離帯**を描く
（`--heatmap-band N` で変更可）。

| 面 | 何が見えるか |
|---|---|
| 左: 選ばれた追従点 | その距離帯で実際に使われる点と、占有半径 |
| 中: 候補の強さ | 候補画素を相関値で色分け（青=紛らわしくない＝良い、赤=紛らわしい） |
| 右: 弱い領域 | 使える手がかりからの距離。**赤い場所には追従の手がかりが無い** |

絵のどこを直せばいいかは右の面で分かる。外周22pxはテンプレートが収まらないので
構造的に対象外（灰色で抜いてある）。

## 11. 検出側を実際に測る（2026-08-12）

10章までは**追従**（`.fset`）の話。こちらは**検出**（`.fset3`）を、
実機もプリントも使わずに測る方法。

### 道具

```bash
cd tools && npm install          # 初回だけ。検出器の実体(49MB)を入れる
python3 tools/check_detection.py ../website/projects/atariar/markers/edo/01 --size 305
python3 tools/check_detection.py --self-test
```

本物の検出器（ARnft が中で使っているのと同じ WASM、`@webarkit/jsartoolkit-nft`
の Node ビルド）に合成した映像を通す。1条件あたり数ミリ秒。

画像の扱いは Python（PIL）、検出は Node、という分担。
`tools/nft_detect.js` は単体で使うものではなく、入口は必ず `check_detection.py`。

### 【最重要】最初に登録された参照画像が丸ごと死んでいる

**公開中の全マーカーが、検出できるはずの条件の 2割弱を取りこぼしている。**

`kpmMatching.cpp` の生きているコードがこうなっている。

```cpp
int matched_image_id = kpmHandle->freakMatcher->matchedId();
if (matched_image_id != 0) {          // ← 本家 artoolkit5 は `if (... < 0) continue;`
    int matchedPageNo = kpmHandle->pageIDs[matched_image_id];
    ...姿勢計算...
}
```

`db_id` は `kpmSetRefDataSet` が (ページ, 画像) の順に **0 から**振る。
マッチャは最も対応点の多い参照画像を**1つだけ**返すので、
**db_id 0 が勝つと、姿勢計算ごと飛ばされて検出が丸ごと失敗する。**
2番手に落ちる仕組みは無い。

症状は「徐々に悪くなる」ではなく「特定の距離でだけ完全に落ちる」。
satoshi/01 の実測（横持ち、対応点つき）:

| 表示幅 | 300 | 260 | 220 | 185 | 155 | 130 | 108 | 92 |
|---|---|---|---|---|---|---|---|---|
| そのまま | × | × | ○62 | × | × | ○19 | × | ○10 |

220px で対応点62 と強く一致するのに 260px で皆無。これは絵の問題ではない。

### 対処: 点を持たないダミー段を先頭に挿す

`.fset3` のページの画像リストの**先頭に、どの点も参照していない段を1つ足す**。
db_id 0 がそのダミーに割り当てられ、**本物の段は全部 db_id ≥ 1 になって生き返る**。

公開中の25マーカー × 11の表示幅で実測（数字は検出できた条件の数）:

| 対処 | 合計 |
|---|---|
| そのまま | 176 |
| 段0を除去 | 175（**効かない**。問題が段1に移るだけ） |
| **ダミー段を先頭に** | **216（+23%）** |

**悪化したマーカーは0本、改善が11本。** しかも改善したのは実機で弱かったものばかり。

| マーカー | 前 | 後 |
|---|---|---|
| satoshi/01 | 3 | 8 |
| tweetybird/02 | 4 | 9 |
| pizzaboy/02 | 4 | 9 |
| edo/01 | 5 | 10 |
| tweetybird/03 | 2 | 6 |
| pizzaboy/04 | 2 | 6 |

「段0を除去」が効かなかったことが、原因が**段の中身ではなく順番**である証拠になっている。

追従（`.fset`）には一切触らないので、姿勢の安定性には影響しない。

### 実測結果（ブラウザ版での最初の確認）

| マーカー | 実機での体感 | 検出限界 |
|---|---|---|
| satoshi/01 | 不安定 | 155px |
| pizzaboy/04 | 同じ絵の繰り返し | 130px |
| satoshi/02 | ほぼ安定 | 90px |
| satoshi/03 | 安定 | 74px |

**実機での体感と順序が一致した。** 対照（マーカー無し）は4本とも未検出。
ただし上の「限界」という言い方は正しくない（次項）。

### 検出できる条件は距離に対して連続しない

飛び地ができる。「300px は駄目なのに 220px は通る」が普通に起きる。
`.fset` の点数のときと同じで、**1つの数字で「限界は◯px」と言うと嘘になる。**
`check_detection.py` は (a) 手前から連続して通る範囲 (b) 通った条件の総数
(c) いちばん遠くで通った距離 の3つを出す。判定に使うのは主に (b)。

### 【最重要】この測定を組むときの落とし穴

**`window.foundCallbacks` と `window.lostCallbacks` を先に定義しておくこと。**

```js
window.foundCallbacks = {};
window.lostCallbacks = {};      // ← ARnft.js を読み込む前に
```

このプロジェクトの `ARnft.js`（`@webarkit/ar-nft` 0.13.1 ベース）は `found()` の中で
この2つを**存在チェック無しに**参照する。本家 0.13.1 には無い独自パッチ。

```js
found(A){ if(A){ if(window.foundCallbacks[this.name])... ; this.target.dispatchEvent(g) }
          else { if(window.lostCallbacks[this.name])... } }
// 呼び出し元:
case"found":this.found(I);break;case"not found":this.found(null)}this._processing=!1
```

未定義だと `undefined[name]` で TypeError。それが `dispatchEvent` の手前、かつ
`_processing=!1` の手前で飛ぶので、**1枚目の返事で固まって以後すべて無反応**になる。
本番の `website/projects/atariar/js/index.js:78-79` はこの2行を先に置いているので動く。

### そのほか、実装時に必要な事実（すべてソースで確認済み）

- **渡す画像は 320x240**。`controller.load()` が `pw=320, ph=240` を算出し、
  worker が `initWithDimensions(pw, ph, ...)` を呼ぶ。640x480 を渡すと
  `dataHeap.set()` が RangeError で落ちて返事が来ない
- **`process(imagedata, frame)` は buffer を transfer する**。同じ ImageData を
  使い回すと2回目に `DataCloneError`。毎回作り直すこと
- **frame 番号は 1 から始め、リセットしない**。worker 側の比較用変数は 0 初期化で、
  同じ値だと処理を飛ばした上に**前回の結果を再送する**（偽陽性になる）
- **検出の合図は `getMatrixGL_RH-<uuid>-<name>` だけ**。`window` に飛ぶ（`document` ではない）。
  未検出は `nftTrackingLost-<uuid>-<name>`。
  **`getNFTData` は起動時に1回飛ぶだけで検出とは無関係**（ここを取り違えると
  「全部検出できた」という嘘の結果になる。実際に一度やらかした）
- **`autoUpdate = false` にしても返答→イベントの経路は切れない**。
  `autoUpdate` は rAF ループの送信側にしか効かない
- **一度検出すると追従モードに入る**。条件を変える前に空の画面を見せて見失わせないと、
  小さい絵でも追従で当たってしまう
- 裏タブで走らせるには rAF を差し替える。`setTimeout` は裏で1秒刻みに落ちるが
  **`MessageChannel` は絞られない**ので、それでイベントループに戻りながら待つ。
  待ち合わせは1本だけにして全コールバックをぶら下げる（空回りループを増やさないため）

### より良い道具が公式にある

**`@webarkit/jsartoolkit-nft` に Node ビルドがある。** ARnft が中で使うのと同じ WASM を
ブラウザもカメラも canvas も無しで叩けて、`{"found":1, "error":0.917}` と
**確からしさが数値で出る**。参照実装は
[`WebARKitLib-rs/tools/jsartoolkitnft-bridge/run.js`](https://github.com/webarkit/WebARKitLib-rs/tree/main/tools/jsartoolkitnft-bridge)。
依存は `sharp` のみ。ブラウザ経路より確実に良いので、次に組むならこちら。

### 存在しなかったもの（探す必要なし）

- ARToolKit5 に `check_nft` のような「検出できるか試す」ツールは**無い**。
  `dispFeatureSet` は点を重ねて描くだけの可視化
- artoolkitX の `check_image_2d_tracking` は名前が紛らわしいが**NFT ではない**
  （OpenCV 版の別トラッカー用）
- 生成器が出す "Confidence level" は画像のエントロピーからの推定で、
  **検出を試してはいない**

## 12. 縦持ちの検出解像度を上げる（2026-08-13、本番投入済み）

**マーカーを1枚も作り直さずに、追従点を 2.3 倍にできた。**
絵の問題でも生成設定の問題でもなく、**映像の渡し方**の問題だった。

### 何が起きていたか

`ARnft.js` の `CameraViewRenderer.prepareImage()` は、映像を
「長辺を320に縮めて 4:3 の画布に収める」。スマホを縦に持つとカメラは
600x800 を返すので、320x240 の中央に 180x240 で置かれ、**左右70pxずつ黒帯**になる。

```js
var A = 320/Math.max(vw, vh/3*4);        // 縦持ち 600x800 → A=0.3
this.w = vw*A;  this.h = vh*A;           // 180 x 240
this.pw = max(w, h/3*4);                 // 320（左右が黒）
```

検出に使える幅が 180px しかなく、**公開中の25マーカーは7割の場面で
追従の下限（3点）を割っていた。** 横持ちなら 320px 使えて安定する。
「横持ちの方が安定する」は設定の違いではなく幾何の結果。

### 【最重要】なぜ 4:3 に固定されていたのか — 設計ではなかった

作者本人（@misdake）が理由を書いている。出典は
[kalwalt/jsartoolkit5#39 のコメント（2020-05-21）](https://github.com/kalwalt/jsartoolkit5/issues/39#issuecomment-632126407)。

> 4:3 because I used a fixed "camera_para-iPhone 5 rear 640x480 1.0m.dat" for
> camera params and **didn't have time to implement a matching**.

設計メモにも「**they may not be necessary, well, at least it works.**」。
つまり「4:3 が良いから黒帯にした」のではなく、**カメラ設定が 640x480 の1個しか
なかったので画布を 4:3 に固定するしかなかった**。時間切れの間に合わせ。

そして**同じ作者が正しい直し方も書いていた。**

> I think 3:4 is doable with that camera params. **rotate video feed 90 degrees
> when drawing onto canvas_process and rotate the perspective matrix back.**

さらに jsartoolkit5 には `ARController.orientation='portrait'` として
実装が入っていた。2022年に webarkit/jsartoolkitNFT が DOM 依存を剥がす整理で
「向きの処理は呼び出し側でやればいい」とされたが、**その呼び出し側の実装は
AR.js にも ARnft にも一度も書かれなかった。** 責任だけ移して誰も受け取らなかった。

**そのコードは今も同梱の ARnft.js の中に残っている**
（`"portrait"===this.orientation` の分岐）。ARnft が常に ImageData を渡すので
到達しないだけ。「削除された」のではなく**到達不能なまま忘れられていた。**

### 採用した対処: 縦持ちなら映像を90度回す

`website/projects/atariar/js/ARnft-rot.js`（`ARnft.js` の改造版。**元は1バイトも変えていない**）。
`index.html` の読み込み先を1行変えるだけで切り替わる。

**変更は3箇所だけ。**

```js
// 1. prepareImage() 縦持ちなら vw/vh を入れ替えて**既存の式に**通す
this.rot = this.vh > this.vw;
var V = this.rot ? this.vh : this.vw,  H = this.rot ? this.vw : this.vh;
var A = 320/Math.max(V, H/3*4);        // 式は元のまま
// 600x800 → V=800,H=600 → 画布 320x240（大きさは変わらない。黒帯が消えるだけ）

// 2. drawImage を回転描画に（getImage と get image の2箇所、中身は同一）
ctx.save(); ctx.translate(pw, 0); ctx.rotate(Math.PI/2);
ctx.drawImage(video, 0,0,vw,vh, oy, pw-ox-w, h, w);   // 導出と画素で検算済み
ctx.restore();

// 3. 射影行列を90度戻し、描画バッファとの縦横比の食い違いも打ち消す
for (var c=0; c<4; c++) { var a=B[4*c], b=B[4*c+1]; B[4*c]=-b; B[4*c+1]=a; }
var k = (ph/pw)*(ph/pw);  B[0]*=k; B[4]*=k; B[8]*=k; B[12]*=k;
```

**3番目の後半（`k`）を忘れると横に 1.78 倍伸びる。** 描画バッファは
`renderer.setSize` で 4:3 のままなのに、回転で射影が実質 3:4 になるため。
実機でも理論値どおり 1.77 の歪みが出た。さらに悪いことに、この歪みは
**画面中央でだけゼロ**で、端に行くほど ±150px ずれる。中央で試すと気づけない。

### 効果（全25マーカーで計算、実機で確認済み）

| | 実効幅 | 追従点の合計 | 追従不能 | 画素比 |
|---|---|---|---|---|
| 元の黒帯方式 | 136px | 96 | 7本 | 1.00 |
| **回転（採用）** | 181px | **218（2.3倍）** | 2本 | **1.00** |

実効幅 = マーカーを画面の見えている幅いっぱいに写したときの、画布上の画素数。
`object-fit: cover` で映像の左右25%は画面に映っていないので、その分を割り引いた値。

実機（iPhone、映像600x800、画面375x664）で確認したこと。
遠ざけても消えない／向き・形・位置すべて正しい／端に寄せてもずれない／重くない。

### 【取っておく案】第2段: 画布を大きくする

**やっていない。必要になったら出す。** 実効幅は画布の高さに比例するので、
画布を大きくすればさらに増える。

| 画布 | 画素比 | 実効幅 | 追従点の合計 | 追従不能 |
|---|---|---|---|---|
| **320x240（現状）** | 1.00 | 181px | 218 | 2本 |
| **400x300** | 1.56 | 226px | **301** | **0本** |
| 440x330 | 1.89 | 249px | 289 | 0本 |
| 480x360 | 2.25 | 271px | 298 | 2本 |
| 568x426 | 3.15 | 321px | 343 | 1本 |

**点数は画布の大きさに単調に増えない。** 距離帯の重なり方が不規則なため。
480 や 568 で追従不能が戻るのはそれが理由。**この中では 400x300 が最良。**

**やり方**: `ARnft-rot.js` の `320` を `400` にする。**ただし2箇所あり、
必ず同じ値にすること。**

```js
prepareImage():    var A = 320/Math.max(V, H/3*4);      → 400
NFTWorker.load():  var g = 320/Math.max(A, I/3*4);      → 400
```

**片方だけ直すと、画布と検出器の初期化サイズが食い違い、
エラーも例外も出さずに一切認識しなくなる**（画素数が同じなので RangeError すら出ない）。
しかも横持ちでは偶然一致するので、横持ちで確認すると通ってしまう。

**426 は使えない**（片方が 319、もう片方が 319.5 になる）。
整数で一致するのは 320 / 400 / 440 / 480 / 568（検算済み）。
`camera_para.dat` は 4:3 のままなので変更不要。

**やらなかった理由**: 実機で全マーカーが問題なく動いており、
残る追従不能2本（emoticons/01、pizzaboy/06）はもともと点数の少ない絵で、
画布を大きくしても 2〜4点にしかならない。根本的には絵の問題。
1.56倍の画素は発熱・電池に効きうるし、確かめ直す手間もかかる。
**具体的な必要が出てから出す。**

### 採らなかった案: 黒帯をやめて縦長の画布にする

一度これで作って実機でも効果が出たが、**捨てた。** 記録として残す。

| | 黒帯撤廃 | 回転（採用） |
|---|---|---|
| 画布の比 | 端末ごとに変わる | **4:3 のまま固定** |
| カメラ設定 | 比ごとに自作が必要（8ファイル作った） | **既存の1つで足りる** |
| 4:3 でない端末 | **静かに壊れる** | 壊れない |
| `initWithEntities(640,480)` の罠 | **踏む（致命的）** | 画布が変わらないので踏まない |
| 変更箇所 | 3ファイル＋設定8個＋起動処理 | **3箇所・約10行** |

**`arParamChangeSize` は縦横を別々の倍率で伸縮する**（実ソースで確認）。
「同じ画角を別の画素数で撮り直した」場合にだけ正しい式なので、
画角の違うフレームに当てると焦点距離が最大33%狂う。
**縦横比の検査も警告も無く、戻り値すら呼び出し側で見ていない。**
だから画布の比を端末ごとに変える設計は、根本的に分が悪い。

### 覚えておくべき罠

- **`NFTWorker` の vw/vh は `initWithEntities(640,480)` の値**であって
  カメラの実サイズではない（`new w(A, this.width, this.height, ...)`）。
  ここを実サイズに変えると `A=1.778` の歪みが復活する。**触らないこと。**
- **補正は射影側だけで行う。** 姿勢側で補正すると 56px ずれ、両方直すと90度傾く。
  数学的に、姿勢は剛体なので射影側の補正（特異値が 1.33/1.0/0.75 で非剛体）を
  再現できない。
- **本番は `getUserMedia` に `height` を渡していない**（`width` だけ）。
  縦横比は端末任せ。さらに `enumerateDevices` の**最後の1つを強制**するので
  `facingMode` は事実上無効。ただし権限が下りる前は列挙できないので、
  初回と2回目でカメラが変わりうる。
- **ARコンテンツは `PlaneGeometry(1,1)` の正方形。** 正面から見て正方形に
  見えるかどうかが、射影が正しいかの目視判定になる。
  なお Javatari の本来の画面比は **1.435 : 1**（canvas の中身は 320x446 だが
  表示は 640x446。Atari の画素は横2倍で表示するのが正しい）。
  つまり**ARの画面は本来より 1.435 倍たてに伸びている。**
  `PlaneGeometry(320/223, 1)` で直るが、各ゲームの `size` の調整が要るのと、
  作品の見え方の話なので保留にしてある。

### 元に戻すには

1. URL に `?rot=0` を足す（デプロイ不要、その場で元の挙動）
2. `index.html` の `<script src="js/ARnft-rot.js">` を `js/ARnft.js` に戻す
3. コミット `dfd49b7` を revert する

## 13. 強化版ジェネレータの構想

現行の NFT-Marker-Creator は「生成はできるが、できたマーカーが良いか悪いか分からない」。
そこを埋めるのがこの2つのツール。

### できたもの

| 機能 | どこ |
|---|---|
| 生成後の自動採点（距離帯ごとの分布・実使用の点数） | `tools/parse_fset.py` |
| **生成前の予測**（同じ判定表を画像だけから出す） | `tools/predict_features.py` |
| **弱い場所の可視化**（3面ヒートマップ） | 同 `--heatmap` |
| 実寸からのdpi計算 | 両方（`--size-mm` / `--dpi`） |
| 使用距離のシミュレーション（縦持ち・横持ち） | 両方 |
| アルファ付きPNGの警告 | `predict_features.py` |

### まだやっていないこと

- **自動探索** … 拡大倍率（1/2/4倍）× level（0〜4）を総当たりして、
  目標点数を満たす最小サイズの組み合わせを提案する。
  予測が1〜4秒で出るようになったので、10通り回しても1分かからない。**次にやるならこれ**
- **既存マーカーとのベンチマーク比較** … 手元の実績あるマーカーと並べて評価する
- **画像の自動前処理** … ニアレストネイバー拡大は効くと分かっている。それ以外
  （コントラスト強調、アンシャープ、ディザ付与など）が効くかは未検証
- **`.fset3`（検出側）の予測** … 今は追従側（`.fset`）だけ。
  「認識しない」系の症状はこちらなので、必要になったら FREAK/SURF 側も再現する

### 設計メモ

- 現行ツールは wasm 版 `genTexData` を叩いているだけなので、**wasm はそのまま使い、
  その前後（前処理と採点）を足す**のが最小の構成になる
- 採点ロジックは Python でも JS でも書ける。`.fset` のフォーマットは単純なので移植は容易
- ローカルCLI版が動く状態になっているので、総当たり探索はそこに載せるのが早い
